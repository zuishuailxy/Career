## 三、架构大纲（面试时口述，四层 + 横切）

讲的顺序建议**自上而下**，因为上层是"为什么这么做"，下层是"怎么落地"，
先给设计意图再给实现，面试官更容易跟上。

### ① 上下文工程层 — 五件套（本项目最有含量的部分）

| 组件 | 代码位置 | 一句话原理 |
|---|---|---|
| Composer | `context/composer.py` | 运行时读工作区的 `AGENTS.md` 与 `.claw/skills/` 元数据，拼进 System Prompt |
| Compactor | `context/compactor.py` | **token 阈值**触发（`estimate_tokens` 保守估算，非字符）；按信息价值分五档淘汰（远期工具输出 → 近期工具输出 → 远期推理 → 近期推理 → 失败记录与指令永不淘汰），降到阈值即停；System Prompt 与 tool_calls 绝不改动 |
| Recovery | `context/recovery.py` | 16 个 `[ERR:CODE]` → 15 条救援提示，把"报错"翻译成"下一步做什么" |
| Reminder | `engine/reminder.py` | MD5(工具名 + 排序后参数) 指纹，同指纹连续失败 3 次注入打断指令 |
| PLAN/TODO | `context/composer.py:27-48` | 由 System Prompt 的 plan-mode 条款强制模型外化进度；`memory/` 包为空，非代码模块 |

### ② 核心引擎层

- **MainLoop**：双阶段 ReAct 循环，`MAX_TURNS=30`
- **Phase 1 慢思考**：只取归一化后的 `reasoning`，注入本轮上下文但**不写入 Session**
  （详见 §9.1）
- **Provider**：`LLMProvider` 抽象基类 + `DeepSeekProvider`（OpenAI 协议）+ `AnthropicProvider`（Anthropic Messages 协议）
- **Semaphore(5)**：工具并发限流 —— 注意它在**引擎层**（`loop.py:52`），不在中间件里

### ③ 工具与执行层

- **Registry**：dict O(1) 路由，靠输出是否以 `[ERR:` 开头**自动判定**成败
- **中间件链**：只负责高危拦截（`allowed, reason` 契约），运行时可动态挂载
- **内置工具 ×6**：`read_file` / `write_file` / `edit_file` / `bash` / `load_skill` / `spawn_subagent`
- **幻觉容错**：模型调了不存在的工具 → 返回 `is_error=True` 的错误消息（不是抛异常）
- **顺序确定性**：并发结果按索引回填 `results[idx]`，保证与 `tool_calls` 同序（详见 §9.2）
- **输出卸载**：`read_file` 超阈值时完整内容落盘，回传头尾预览 + 路径引用（详见 §9.3）

### ④ 入口交互层

- **CLI 终端**：默认不挂审批中间件 → YOLO 模式
- **飞书长连接**：WebSocket AgentOps，按 chat_id 隔离 Session
- **Human-in-the-loop**：`asyncio.Future` 挂起 + 飞书文本 `approve <task_id>` 放行 + 300s 超时自动拒绝

### 横切能力（不属于任何一层，独立成体系）

CostTracker 装饰器计费 · 自研 ContextVar Span 链路树 · Benchmark 沙箱跑分与 waste_ratio 指标
· **配置层 `src/tiny_claw/config.py`**（模型名 / 端点 / 凭据 / 压缩阈值 / 工具预算的唯一来源）

> 配置层看着不起眼，但它值钱的地方在于**让跨模块的常量关系变得可检查**。
> 例子：本次把常量抽过去之后，`read_file` 的单次输出预算和 `Compactor` 的全局阈值
> 第一次能被放在一起比较，立刻暴露出「中文项目里读一次文件就顶爆全局预算」
> 这个此前分散在两个文件里、谁也看不出来的冲突（详见第七节第 9 条）。

## 四、核心实现（逐条，可直接改成简历 bullet）

### 1. 双阶段推理循环：推理链只入上下文，不入历史

DeepSeek reasoner 模式下有个坑：`content` 里会混入**模型假造的 XML 工具调用**，
直接用会污染工具解析。所以只取 `reasoning_content` 字段。

更关键的是第二个决策：推理文本**只注入本轮上下文，不 append 进 Session**。
因为 Compactor 按 token 配额压缩，推理链一旦入历史就会把真正的工具结果挤出去——
Agent 会"记得自己怎么想的，忘了工具返回了什么"。

```python
# loop.py:89-99
think_resp = await self.provider.generate(context, None)   # tools=None → 触发慢思考
if think_resp.reasoning_content:
    context.append(Message(role=Role.ASSISTANT, content=thinking_content))  # 只进 context
# 注意：没有 session.append()
```

### 2. 上下文压缩：按信息价值分级淘汰 + 配对保护

难点不是"截断"，是**不能破坏 tool_call / tool_result 的配对**——
截出一条没有对应 tool_call 的 tool 消息，OpenAI 协议直接 400。

淘汰顺序（档位数字越大越先被丢）：

| 档位 | 内容 | 动作 | 为什么这么排 |
|---|---|---|---|
| 4 | 远期成功的工具输出 | 全量掩码（保留原始长度提示） | 信息已被模型消化，且可用 `read_file` 的 offset/limit 重新取回 |
| 3 | 近期成功的工具输出 | `head 500 + tail 500` | 命令回显的头部有价值、报错堆栈在尾部 |
| 2 | 远期模型推理 | 折叠成一行 | 体积小，但承载决策链 |
| 1 | 近期模型推理 | 折叠成一行 | 同上，最后才动它 |
| 0 | System / 用户原始指令 / **失败记录** | **永不淘汰** | 失败记录含 `[ERR:CODE]` 与救援提示，丢掉会让模型重复踩同一个坑 |

两个值得讲的设计判断：

- **渐进式，够用就停**：从最低价值档开始淘汰，一降到阈值以下立即停手。
  旧实现是"一超阈值就把全部远期历史一次性掩码"，属于过度压缩——
  明明只超了 1000 token，却丢掉 8000 token 的历史。
- **失败记录的优先级是反直觉的**：直觉上"失败的尝试没价值"，恰恰相反——
  成功的输出早已被消化进后续决策，而失败记录是模型唯一的"这条路走不通"的记忆。

其余不变：System Prompt 与 `tool_calls` 字段**永不改动**（维系逻辑链）；
`Session.get_working_memory()` 额外做孤儿清理，丢弃首条为 tool 响应的消息。

### 3. 错误码驱动的自愈闭环

工具层统一输出 `[ERR:CODE] message`，Registry 靠**前缀自动判定**是否失败，
工具自己不需要声明成功与否：

```python
# registry.py:112
is_error = output.startswith("[ERR:")
```

RecoveryManager 用表驱动把 16 个错误码映射成 15 条救援提示。
设计上有个刻意的取舍：**UNKNOWN 不映射**——不认识的错不给提示，
留给模型自己分析，避免错误引导。

举例，`EDIT_OLD_TEXT_NOT_FOUND` 的提示不是"编辑失败"，而是：
> "请先使用 read_file 工具重新读取该文件，获取最新内容后再重新发起编辑。"

### 4. 指纹死循环打断

```python
# reminder.py:39-43  参数先 sort_keys 再 dumps，避免键顺序影响指纹
args_json = json.dumps(arguments, sort_keys=True, ensure_ascii=False)
return hashlib.md5(f"{tool_name}:{args_json}".encode()).hexdigest()
```

连续同指纹失败 3 次 → 注入打断消息；**任意一次成功即清空全部计数器**（说明走出死胡同）。
打断消息的注入位置有讲究：放在**所有工具结果之后**（`loop.py:180`），
否则会插在 tool_call 和 tool_result 中间，破坏配对。

### 5. 只读子智能体 + Protocol 打破循环依赖

主 Agent 探索大仓库会把上下文撑爆。解法是派一个子 agent：

- **物理只读**：子 agent 的 registry 只注册 `read_file` + `bash`，它拿不到写工具
- **资源隔离**：独立 Semaphore、独立 RecoveryManager、独立 System Prompt、10 轮上限
- **只回摘要**：几万字的探索过程压缩成一段总结返回给主 agent

架构上有个真问题：tools 包要拉起 engine，会循环 import。解法是
`@runtime_checkable Protocol` 定义 `AgentRunner` 契约，工具只依赖抽象：

```python
# subagent.py:23-47
class AgentRunner(Protocol):
    async def run_sub(self, task_prompt: str, read_only_registry: Registry, ...) -> str: ...
```

### 6. 飞书人工审批回路（Human-in-the-loop）

Agent 手上有 bash 和 write_file，直接上线等于给实习生 root 权限。

- **中间件机制**：`Registry.use(mw)`，`mw` 返回 `(allowed, reason)`，任一拦截即终止
- **分级策略**：`read_file` 白名单放行；`write_file`/`edit_file` 一律审批；bash 按 8 条高危正则匹配
- **挂起实现**：`asyncio.Future` + 8 位 task_id，飞书回复 `approve <id>` 回调 `set_result` 唤醒
- **fail-closed**：300 秒超时**自动拒绝**，不是自动放行

### 7. edit_file 四级模糊匹配

LLM 输出的 `old_text` 缩进/换行常对不上，硬匹配失败率高。四级降级：
精确 → 换行符归一化(`\r\n`→`\n`) → trim 空格 → **滑动窗口逐行去缩进匹配**。
匹配到多处时直接报 `EDIT_MULTIPLE_MATCH` 让模型补上下文，而不是猜一个。

### 8. 可观测 + 自评测

- **CostTracker**：装饰器模式包装 Provider，透明统计 Token 与人民币成本（内置定价表；
  未收录的模型会**告警而不是静默算 0**，避免成本数据悄悄失真）
- **自研 Span**：ContextVar 在 asyncio 协程间传递父子关系，导出 JSON 链路树到 `.claw/traces/`
- **Benchmark**：每用例物理隔离沙箱（独立目录/引擎/Session），setup → 执行 → validate 脚本判定
- 自定义 **`waste_ratio`** 指标：首次出错后消耗的 Token 占比，衡量"执行顺滑度"而不只是成功率

### 8.1 基线实测：一次录制、离线重放，调参零 API 成本

调阈值最烧钱的做法是「改数字 → 真跑 → 看效果」循环。做法是**把跑分变成语料采集**：

- `eval/instrument.py` 三件插桩（Tracker/Compactor/Registry 代理）在一次跑分里录下：
  ① 每次调用的「本地估算 vs 真实计费 token」；② 每次工具输出体积分布；
  ③ 每轮压缩前的完整上下文快照
- `tools/replay_thresholds.py` 拿语料在本地重放任意阈值组合（正规方程最小二乘校准 +
  网格搜索），**API 成本为 0**，输出每个阈值的触发率/压缩后峰值/误伤条数与推荐档

**2026-09-09 基线**（4 用例：edit / code_gen / big_read / multi_step）

| 指标 | 数值 | 口径与出处 |
|------|------|------|
| 任务成功率 | **4/4** | 分两轮凑齐：首轮 4 用例产出全对，其中 2 个被**判卷脚本**误判为失败（BSD grep 不支持 `\|` 交替）；修脚本后重跑这 2 个 → 2/2 通过 |
| API 成本 | **≈ ¥0.15** | 两轮合计（首轮 ¥0.106 + 重跑 ¥0.045）。**单个报告文件里只有 ¥0.045 那个数**，因为重跑覆盖了首轮报告 |
| 校准模型 | real ≈ **309 + 1.86×est + 55.8×消息数** | 最小二乘拟合，来自全量语料的 `threshold_report.json`（slope 1.858 / intercept 309.5 / per_message 55.79） |
| 本地估算偏差 | 旧系数**低估 1.86 倍** | 且每条消息 ~56 token 的结构开销此前完全没算 |
| 上下文峰值 | est 1797 → 真实 **≈4652 token** | 旧阈值 8000 在全部语料上**零触发** |

⚠️ **三条必须自己先讲清楚的口径问题**（否则被追问会答不上来）：

1. **阈值 16000/32000 不是重放"推导"出来的**。重放脚本的推荐逻辑是「取第一个够用的档位」，
   它给的是 **8000**。实际落到 16000/32000 的依据是**等比重标定（×4）**：
   系数修正后 est 值整体放大 1.86 倍，再乘 2 倍余量，使**触发行为与旧版近似等价**——
   这是工程裁量，不是数据最优解。老实说这句，比假称"数据算出来的"安全得多。
2. **重放里所有档位的触发率都是 0**。因为语料峰值（est 1797）连最小的 8000 档都没够到。
   所以重放的真正价值是两件事：**校准系数** + **暴露「旧阈值从未触发」**，
   而不是"在网格里选出了最优阈值"。
3. **报告文件的状态**：本机 `.claw/sandbox/benchmark_report.json` 是**重跑留下的 2 用例版**，
   不是 4/4 的完整证据；且 `.claw/sandbox/` 被 `.gitignore` 忽略（不入库）。
   被问到就说"报告是本机产物、未入库，可以当场重跑复现"。

面试要点：**估算系数不是拍的**——如果没有插桩校准，0.25 token/字符的旧系数
会一直带着「阈值 8000、实际 15000」的幻觉跑下去；而校准这件事本身，就是
「先计量、再调参」最硬的证据。

### 9. 模型兼容层：一套引擎，两套协议

**三句话定位（口述用）**：

1. 引擎只认内部 Schema（`Message` / `ToolCall` / `ToolDefinition`），
   不知道世界上存在 OpenAI 还是 Anthropic。
2. Provider 层负责**双向翻译**：出站把内部结构翻成厂商格式，入站把厂商响应反解回内部结构。
3. 抽象层成不成立的判据只有一个：**换协议时上层代码改动量**。本项目是 0 行。

要讲清楚一件事：这不是"支持了很多模型"，而是**把厂商协议差异挡在引擎之外**，
并且用「同模型双协议」的方式做了对照验证。

DeepSeek 官方在 `https://api.deepseek.com/anthropic` 提供了 Anthropic 协议端点，
因此 `DeepSeekProvider`（OpenAI 协议）与 `AnthropicProvider`（Anthropic Messages 协议）
可以指向**同一个模型** —— 同厂商、同模型、仅协议不同，
跑出的任何差异只能归因于协议翻译层本身。这是最干净的对照实验。

> 模型名由配置层统一给定（`TINY_CLAW_MODEL`，默认 `deepseek-v4-flash`），
> 两个 Provider 读的是同一个值，从机制上杜绝了"两边跑了不同模型"导致的伪结论。

六处结构性差异及处理：

| 差异点 | OpenAI 侧 | Anthropic 侧 |
|---|---|---|
| System Prompt | `messages[0] role=system` | 顶层 `system` 字段 |
| 工具调用 | `tool_calls` 字段 | content block 的 `tool_use` |
| 工具结果 | `role="tool"` 独立消息 | user 消息里的 `tool_result` block |
| **连续工具结果** | 多条独立消息 | **必须合并进同一条 user** |
| 停止信号 | `finish_reason="tool_calls"` | `stop_reason="tool_use"` |
| 推理链 | `reasoning_content` | `thinking` block |

后两行才是抽象层真正的考验：

- 内部 Schema 是「一条消息一个工具结果」，映射到 Anthropic 时**必须做合并**，
  否则协议报错——这正是"抽象层照着 OpenAI 形状设计"会漏掉的地方
- 两家私有推理字段统一归一化到 `Message.reasoning`，引擎对厂商完全无感

**验证方式**：`pytest -q` 共 **132 个用例**，其中 **20 个是双协议翻译对照用例**，
验证同一组内部 Message 经两条路径后语义等价（纯函数级，**不需要 API Key**）。

⚠️ 仍要诚实标注：**尚未用真实 API 跑通过端到端**（已配 Key 但未花这一步的钱，
见第七节第 4 条，两条命令各几分钱）。单元测试证明的是翻译逻辑正确，不是网络链路可用。

### 9.1 慢思考（Phase 1 Thinking）：难点不在"想"，在"想完之后"

**一句话**：每一轮行动前先单独调一次模型做纯推理，把推理链注入本轮上下文，
但**不写进 Session**；然后带着工具定义再调一次做真正的行动。

关键实现（`engine/loop.py:87-104`）：

```python
# Phase 1：available_tools=None → 不传 tools 字段 → 触发纯推理模式
think_resp = await self.provider.generate(context, None)
if think_resp.reasoning:                      # 归一化字段，引擎不感知厂商
    context.append(Message(role=Role.ASSISTANT, content=think_resp.reasoning))
    # 注意：只 append 到本轮 context，没有 session.add_message()

# Phase 2：带工具定义再调一次
response = await self.provider.generate(context, available_tools)
```

**三个设计决策及原因**（这才是面试要讲的部分）：

| 决策 | 代码位置 | 为什么 —— 不这么做会怎样 |
|---|---|---|
| 用 `reasoning` 而非 `content` | `loop.py:94` | reasoner 在纯推理模式下会把"假工具调用"以 XML 形式吐进 `content`。直接喂给 Phase 2 会污染后续决策 |
| **推理链不写 Session** | `loop.py:106-107` | 推理链动辄几千字。写进 Session 就吃 Compactor 的 **token 配额**，把真正的工具结果挤出去——这是最隐蔽的一个坑，症状是"agent 越跑越蠢" |
| Compactor 阈值联动 | `loop.py:44-49` | 开慢思考 8000 token / 保留 10 条；关闭则 4000 / 6。因为推理文本本身要占地方，阈值不抬高等于变相缩短记忆 |

**第三个决策值得单独讲**：慢思考不是免费的，它多花一次 API 调用、
多占上下文预算。设计者必须回答"代价换来什么"——
本项目换的是**决策质量**，代价用"不写 Session + 抬高阈值"两招对冲掉。
能讲清这笔账，比说"我加了慢思考"高一个层级。

**双协议下如何保持一致**：契约是"`available_tools=None` 即进入思考"。

| 协议 | 触发方式 |
|---|---|
| OpenAI | 不传 `tools` 字段（`openai.py:156-158`）|
| Anthropic | 改传 `thinking: {type: "enabled"}` block（`anthropic.py:256-264`）|

引擎侧完全一样的一行 `generate(context, None)`，两种协议各自翻译成自己的开关方式。
这是"抽象层成立"的第二个证据（第一个是 §9 的六处差异）。

⚠️ **诚实标注**：慢思考**没有 A/B 实测数据**——仓库里没有 benchmark 报告。
面试时说"我这样设计的理由是 X"，不要说"实测效果提升 Y%"。
要补数据就跑：`python main.py -p "..." --provider openai` 对比 `--no-thinking`。

### 9.2 工具注册与分发：把"失败"当成一种返回值，而不是异常

**一句话**：`BaseTool` 抽象三方法（`name` / `definition` / `execute`），
`RegistryImpl` 用 dict 做 O(1) 路由，中间件链式拦截，执行结果统一封装成 `ToolResult`。

看起来平平无奇，但里面有五个**只有做过 agent 才会想到**的设计：

| # | 设计 | 代码 | 为什么 —— 换个做法会怎样 |
|---|---|---|---|
| 1 | **幻觉容错**：工具名不存在 → 返回错误消息，不抛异常 | `registry.py:81-84` | 模型调了不存在的工具是常态。传统服务里 404 是错误，**agent 里 404 是反馈**——把"没有这个工具"告诉模型，它下一轮会自己纠正。抛异常则直接终止整个任务 |
| 2 | **失败下沉到输出层**：`output.startswith("[ERR:")` 自动判 `is_error` | `registry.py:112` | 不用异常表达业务失败。异常会打断循环，而前缀只是个字符串，工具自己就能决定"这是失败但可恢复"。同一条前缀还被 RecoveryManager 解析成错误码——**一条链路打通** |
| 3 | **拦截也伪装成工具失败**：中间件拒绝后返回 `is_error=True` 的 ToolResult | `registry.py:95-99` | 对 LLM 来说"被人类拒绝"和"工具报错"是同一种信号，模型用同一套逻辑处理。如果设计成另一种返回形态，模型就得学两套 |
| 4 | **并发结果按索引回填** | `loop.py:124-144` | `asyncio.gather` 完成顺序不确定，但 `results[idx] = ...` 保证结果顺序与 `tool_calls` 一致。若用 `append`，同一任务每次跑出来的上下文顺序都不同 → **不可复现**；Anthropic 侧还要把多个结果合并进一条消息，顺序错了语义就错 |
| 5 | **调度策略不在 Registry** | `loop.py:52` | `Semaphore(5)` 在引擎层。Registry 只管"路由 + 拦截 + 执行"，并发度由调用方决定——关注点分离，子 agent 想换并发度不用改工具层 |

**最值得讲的是第 4 条**，因为它是"看不见的坑"：并发执行天然导致顺序抖动，
而 LLM 对上下文顺序敏感。很多人写完 `gather` 直接 `append`，测试时看不出问题，
上线后表现为"同样的任务，有时成功有时失败"——最难排查的那种 bug。

**另外两条加分项**：

- **重名注册记 warning**（`registry.py:58-59`）：工具名冲突是静默 bug 高发区，
  这里选择覆盖但留痕，而不是直接崩或无声替换。
- **中间件运行时动态挂载**（`main.py:178`）：同一个 registry 实例，
  CLI 模式不挂（YOLO），飞书模式挂审批——**安全策略与工具实现解耦**。

**面试口述 30 秒**：

> 工具层最关键的一个判断是：**失败不抛异常，而是返回一个带错误标记的结果**。
> 因为 agent 是循环的，异常会打断循环，而错误结果是喂回给模型的反馈，
> 模型看到 `[ERR:FILE_NOT_FOUND]` 就知道该先读文件再编辑。
> 工具名不存在也是一样——返回"没有这个工具"让它自己改，整个任务不中断。

### 9.3 长文件读取：三层防御，以及一个只在中文下发作的 bug

**背景**：原实现是 8000 字符**硬截断**——读 20000 行的核心业务类，
模型永远看不到后半部分，任务必然失败。

**改造后的三层防御**（`tools/builtin/read_file.py`）：

| 层 | 机制 | 作用 |
|---|---|---|
| 1 | **局部读取** `offset` / `limit` | 模型按行号按需翻阅，输出带行号前缀 |
| 2 | **输出卸载** Offloading | 超阈值 → 完整内容落盘 `.claw/offload/`，回传「行数 + 头尾预览 + 路径 + 用法」 |
| 3 | **硬截断** | 兜底，保证单次输出永不撑爆上下文 |

**⚠️ 关键设计洞察：卸载必须和 offset/limit 配套做**

讲义说卸载能"倒逼模型按需局部读取"——但**原 `read_file` 没有 offset/limit，
模型根本无法局部读取**。只做卸载的话：读全文 → 超阈值 → 卸载 → 再读全文 → 又卸载，
而且这个循环**现有防线抓不住**：Reminder 的 MD5 指纹只检测 `is_error` 的失败，
卸载返回的是正常结果（`is_error=False`），所以会一路跑到 `MAX_TURNS=30`。

这是"照着讲义做一半会踩的坑"，也是面试时最有说服力的一类故事。

**顺带修掉的静默 bug（实跑验证）**：

```python
# 旧实现：判断用字节，切分用字符
if len(content.encode("utf-8")) > MAX_BYTES:   # 字节
    content = content[:MAX_BYTES]              # 字符 ← 口径不一致
    + f"...[已截断至前 {MAX_BYTES} 字节]..."     # 提示语与事实不符
```

| 输入 | 旧实现返回 | 提示语宣称 |
|---|---|---|
| 英文 10000 字 | 8034 字节 | 8000 字节 ✅ |
| **中文 10000 字** | **24034 字节** | 8000 字节 ❌ |

UTF-8 一个汉字 3 字节，8000 字符 = 24000 字节。**英文项目下完全正常，
只有中文内容才发作**——你的项目注释全是中文，一直在吃 3 倍于设计的上下文。
同类措辞问题还有 `compactor.py` 两处（把"字符"写成"字节"），一并修正。

**✅ 已解决（2026-09-09 补做）**：计量单位已从字符改为 **token 估算**
（新增 `context/tokens.py`，正则区分 CJK，中文 1 字 ≈ 1 token、英文约 4 字符 1 token）。
阈值采用 **1:1 保守换算**（8000 字符 → 8000 token），因此：
中文项目行为与改造前**完全一致**、英文项目获得约 **4 倍**余量——是纯改进，不是调参。

⚠️ **仍未解决的部分**：**阈值数字本身偏小**。8000 token 只占 1M 窗口的 0.8%，
确实浪费；但上调到多少必须有 benchmark 数据支撑，否则就是拍脑袋。
（另一个刻意保留的设计：阈值判定用 token，而掩码/截断提示语报**字符数**——
模型靠字符数判断"值不值得重读"，对 token 没有体感。）

**验证**：`tests/test_read_file.py` 20 个用例，含中文回归用例、
卸载后读回用例（证明不制造死循环）、真实 140KB 日志用例。

### 9.4 System Reminders：运行时状态回灌

**一句话**：System Prompt 回答「你是谁」，System Reminder 回答「现在发生了什么」。
后者必须是动态的——轮数、上下文压力这些状态在启动时根本不存在，
模型看不见，就只能撞到南墙（跑满轮数被强制掐断、历史被静默压缩）。

先把边界划清楚，这是最容易被混为一谈的地方：

| | System Prompt | System Reminder |
|---|---|---|
| 生成时机 | 启动/每轮组装，内容固定 | 运行时条件触发，内容随状态变 |
| 位置 | 首条 / 协议顶层字段 | 对话中途 |
| 本项目 | `PromptComposer`（身份 + 纪律 + AGENTS.md + Skills） | `ReminderInjector` + `ReminderBus` |

**三条硬约束**（缺一条提醒就退化成噪声，这是实现时真正要想的部分）：

| 约束 | 实现 | 不这么做会怎样 |
|---|---|---|
| **冷却** | 同类提醒 N 轮内不重发（`ReminderBus._in_cooldown`） | 每轮都喊"上下文快满了"，模型的反应不是收敛而是**麻木**，还白烧一轮 token |
| **限流** | 单轮最多 N 条（`max_per_turn`） | 多条同时出现时，模型往往一条都不听 |
| **不写 Session** | 每轮重算，只进当轮 context | 累积成历史垃圾，并污染成本统计 |

**注入位置固定在「工作记忆之后、压缩之前」**：放在末尾注意力最好；
先压缩再追加则提醒会被一起清掉。

**协议约束（值得单独讲）**：提醒用 `Role.USER` 而非 `SYSTEM`——
不是偷懒，是协议不允许在对话中途插 system 消息（OpenAI 的 system 在首条、
Anthropic 在顶层字段）。所以只能借 user 通道，
靠 `[SYSTEM REMINDER` 前缀 + `is_system_reminder` 标记声明"这条不是用户说的"。

**顺带修掉的静默 bug（这是本节最有价值的部分）**：
提醒走 user 通道且没有 `tool_call_id`，而压缩器的分档逻辑是
「无 tool_call_id 的 USER 消息 = 用户原始指令 → 永不淘汰」。
于是**每一条打断消息都被当成用户原始指令永久保留**。
危险的是它形成正反馈：上下文越满 → 越容易失败 → 越多打断 → 越多永生消息 → 上下文越满。

修法（`compactor.py`）：给 `Message` 加 `is_system_reminder` 标记，
新增 `_TIER_REMINDER_OLD` 档位与专用掩码动作——
**近期提醒保留**（模型得先看见才谈得上响应），**跑出工作记忆窗口的即可清理**。
用户原始指令的永生语义不受影响（有测试守着）。

**验证**：`tests/test_reminders.py` 14 个用例，覆盖触发条件、冷却、限流、
指纹稳定性（参数键顺序不影响）、以及分档行为（远期清理 / 近期保留 / 用户指令不误伤）。

| 为什么不直接用 LangGraph？ | 依赖里有 langgraph，但 Agent Loop 是手写的。理由：agent 循环的核心价值在循环本身的**可控性**（压缩时机、打断时机、并发度），框架把这些藏起来了，就没法调了 |
| 慢思考为什么不写进历史？ | 推理链动辄几千字，写进 Session 会吃掉 Compactor 的 **token 配额**，把工具结果挤出去。设计判断是：对后续决策更值钱的是"工具返回了什么"，不是"模型刚才怎么想的"。⚠️ **注意：这是设计推理，不是实测结论——仓库里没有 benchmark 报告，别用"实测"这个词** |
| 子 agent 为什么给 bash？bash 不就能写文件了吗？ | ⚠️ **这是真问题，别装作没有**。bash 确实可以写，当前只读约束是**意图层**不是**强制层**。正确答法：真正的强制需要在 OS 层做沙箱（容器/受限用户/只读挂载），当前实现是纵深防御的第一层 |
| MCP 你做过哪一侧？ | **两侧都有，但口径要分清**：早期课程项目 `MCP-A2A/` 是用 `python_a2a` 的 FastMCP 写的 **Server 侧**（协议细节被库封装）；本项目里是自研的 **Client 侧**——连接标准 MCP server、发现工具、包装成 `BaseTool` 注册进 Registry，协议交互（initialize / tools/list / tools/call）自己碰。**别混成一句"我做过 MCP"**，追问"server 还是 client"就散了 |
| 这些功能有现成的库，为什么自己写？ | **先分清哪部分是"现成的库"**：MCP 的协议层（JSON-RPC / stdio 传输 / 握手与发现 / list 与 call）全用官方 `mcp` SDK，我一行协议都没实现。但评测/压缩/双协议这些**框架内层**没法外包——`langchain-mcp-adapters` 之类输出的是 LangChain 的 Tool 抽象，塞进来会同时破坏三样东西：`[ERR:CODE]` 自愈体系、审批中间件、以及刻意的"不依赖 LangChain"（LangGraph 同理，循环手写是为了保住压缩/打断/并发的**控制点**）。**甄别标准**：替换后是否丢失本项目既有契约——丢契约的不能外包，只是重写一遍库已有机制的就不该自己写 |
| MCP 规范现在是什么状态？ | **2026-07-28 刚做了史上最大改版：协议层去掉会话**——移除 `initialize` 握手与 `Mcp-Session-Id`，每个请求自带 `_meta`，改用可选 `server/discover`；服务端主动请求（elicitation/sampling/roots）改成 **MRTR**（返回 `input_required`、客户端带答案重试）；列表结果可缓存（`ttlMs`/`cacheScope`）。但我**实测**当前生态没迁完：filesystem server 对 `discover` 回 `Method not found`，只能走旧握手协商到 2025-11-25。**这条兼容现在由官方 `ClientSessionGroup` 承担**（实测它对旧规范 server 自动降级、并容忍 prompts/resources 缺失只告警）；我自己的价值不在协议层，而在配置降级、适配、错误码与审批接缝。说「接管了跨代兼容的连接」，别说「按最新规范重写」 |

| 并发执行怎么保证顺序？ | `asyncio.gather` 完成顺序不确定，但用预分配索引 `results[idx] = ...` 回填，保证结果与 `tool_calls` 同序。若用 append，同一任务每次上下文顺序都不同 → 不可复现；Anthropic 侧多结果要合并进一条消息，顺序错则语义错 |
| 并发度为什么不放 Registry 里？ | 关注点分离：Registry 只管路由/拦截/执行，调度策略由引擎决定。子 agent 若想换并发度不用动工具层 |
| 长文件为什么不用更长的上下文硬扛？ | 成本与注意力衰减。卸载 + 按需分段是工业界主流：模型只需要看到"这个文件有多大 + 首尾长什么样 + 去哪取全文"，决策信息量并不比全文少多少 |
| 有 System Reminders 吗？和 System Prompt 什么区别？ | Prompt 静态、回答「你是谁」；Reminder 动态、回答「现在发生了什么」。提醒必须带**冷却 + 限流 + 不写 Session** 三约束，否则就是噪声。协议不允许中途插 system 消息，所以提醒走 user 通道 + 独立标记 |

## 八、面试速记卡（当天开考前 5 分钟扫这一页）

### 1. 项目一句话（30 秒版）

> 用 Python 复刻并重写了 Go 版 tiny-claw，实现了 **5534 行**的自主编码 Agent 运行时：
> 双阶段推理循环、工具注册与并发调度、上下文压缩、错误自愈、链路追踪，
> CLI 与飞书双入口，**110 个单测全绿**。

**定位纪律**：说「最小可用运行时」，不说「功能完整的 Agent 框架」；
说「星型主从委派」，不说「Agent Team」。

### 2. 六个亮点，每个先背一句话

| # | 一句话 | 追问就展开 |
|---|---|---|
| 1 | **上下文压缩按信息价值分五档渐进淘汰**，而不是按时间一刀切 | 远期工具输出先掩码（可用行号重取）、推理次之、失败记录最后（含错误码与救援提示）、System/用户指令永不淘汰 |
| 2 | **计量从字符改成 token，系数是 benchmark 校准出来的**（旧系数低估 1.86 倍） | 先插桩量、再校准、最后才调阈值——顺序不能反 |
| 3 | **一次录制 + 离线重放**，调参 API 成本为 0 | 把跑分变成语料采集，网格搜索在本地跑 |
| 4 | **长文件三层防御**：行号分段 / 输出卸载 / 硬截断 | 卸载与分段必须配套，否则「读全文→卸载→再读」死循环 |
| 5 | **错误自愈**：16 个错误码 + 15 条表驱动救援提示 + 指纹死循环打断 | 失败是返回值不是异常；报错改写成「下一步动作指引」 |
| 6 | **一套引擎两套协议**，同厂商同模型做对照实验 | 六处结构性差异，关键是「连续工具结果必须合并进一条 user 消息」 |

加分项（被问到再讲）：System Reminders 运行时回灌、飞书人工审批回路、
Provider 层 Protocol 打破循环依赖。

### 3. 必须记住的数字（每个都能当场复现）

|---|---|

### 4. 三个「千万别吹」的雷区

1. **慢思考没有 A/B 数据** → 说"设计理由是 X"，不说"实测提升 Y%"
2. **错误自愈没有减少重试的百分比** → 说"旨在减少无效重试"
3. **双协议没有端到端跑通过** → 说"单测验证了翻译逻辑"，不说"验证过链路"

### 6. 讲故事的三个长度

- **30 秒**：项目一句话 + 一个最硬的亮点（选 #2 校准）
- **3 分钟**：四层架构（context / engine / tools / 入口）+ 六个亮点各一句
- **10 分钟**：挑 2 个亮点深讲——**压缩的五档分级** + **校准→重放→调参的闭环**，
