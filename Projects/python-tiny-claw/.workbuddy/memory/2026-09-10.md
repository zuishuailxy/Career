## 11:30 工具并发讲解（engine/loop.py:133-206）

- 并发源头在模型：一次响应吐 N 个 tool_calls，引擎必须 fan-out。
- 三要素：限流（Semaphore(5)）→ 保序（results[idx] 按下标回填，非完成顺序）→ 兜底（异常降级，杜绝孤儿 tool_call）。
- 协议约束：tool 结果消息必须紧跟 assistant 且顺序一一对应，缺一条下一轮请求即 400。
- 讲清三条未修边界：读写未分类（edit 同文件 read-modify-write 竞态）、信号量范围过大（飞书审批占槽 ≤300s）、无全局预算。

## 17:00 Session 设计讲解（engine/session.py 全文仅 103 行）

### 结构
- `Session`：身份（id/work_dir/时间）+ `_history`（list[Message]，asyncio.Lock）+ 计费（token/cost）+ 容错（error_turns / first_error_token / total_turns）。
- `SessionManager` + `global_session_mgr` 全局单例：dict[会话标识 → Session]，带锁。
- 职责边界很窄：**不压缩、不持久化、不感知工具与 LLM**。

### 三个关键设计决策
1. **压缩在 Session 之外**：Compactor 对 working_memory 副本操作，历史保持完整原样（"全量事实源 + 每次请求前视图压缩"）。
2. `get_working_memory(limit)` 截断时 `while recent[0].tool_call_id: pop(0)` —— 剔除头部孤儿工具响应，与并发段的配对约束呼应。
3. 慢思考 reasoning 只注入本轮上下文、不写 Session，避免挤占 Compactor 配额。

### 发现的问题（未修，待定）
1. **无持久化**：进程重启即失忆，只有 trace 落盘（tracing.export_trace）。CLI 跨进程"断点续传"名不副实。
2. **无容量上限、无 TTL**：`_history` 只增不减（压缩的是副本），SessionManager 字典永不清理 → 飞书常驻进程内存单调增长。
3. **同 chat_id 并发无锁**（bot.py:109 `asyncio.create_task`）：同一会话连发两条消息会并发跑两个 `engine.run(sess)` 共享同一 Session → 两轮的 assistant/tool 消息交错 → tool_call 配对错乱。Session 的锁只保证单次 append 原子，不保证一轮的原子。
4. **reporter 串台**（bot.py:124）：`self._reporter` 是 bot 实例级字段，多会话并发时被后来者覆盖，前一个 engine 可能把消息发到错误的 chat。
5. 两级口径不一致：working memory 按「条数」（20），Compactor 按 token，长工具输出场景下每轮都会触发压缩。

### get_working_memory 补充发现（未修）
1. **原始用户指令会掉出窗口**：`WORKING_MEMORY_LIMIT=20`（条）是硬窗口，长会话跑十几轮后第 1 条 USER（任务目标）
   就滑出窗口；Compactor 的 `_TIER_IMMORTAL` 只保护"窗口内"的 USER 消息，救不回已被切掉的。
   现靠 plan_mode 的 PLAN.md 落盘 + system prompt 缓解。
2. **极端清空**：`while recent[0].tool_call_id: pop(0)` —— 若窗口内全是 tool 响应（并发工具数 ≥ 窗口大小），
   会被全部 pop 到空列表，该轮只剩 system prompt。默认 MAX_PARALLEL_TOOLS=5 安全，调大需复查。
3. 只剔除头部**连续**孤儿，中间孤儿不处理（正常写入路径不会产生）。

  与之前记忆里的 `MAX_TURNS=30` / `Compactor(max_chars=8000)` 硬编码版本不同，以当前文件为准。
