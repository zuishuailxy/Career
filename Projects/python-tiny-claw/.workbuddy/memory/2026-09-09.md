## 补充：课程架构图核验 + 修正版架构整理

用户贴了一张极客时间风格的 Agent 四层架构图（上下文工程/核心引擎/工具执行/入口交互），
问是否就是本项目架构。逐块比对源码后结论：**骨架对，5 处出入，3 个图里漏掉的亮点**。

### 已核实的关键口径（后续不要再说错）

1. Compactor 触发条件是**字符数**（max_chars=8000/4000），**不是 token**。
   Token 监控在 CostTracker，只计费、不触发压缩。机制是双层降级而非"阶梯"。
2. **并发控制在引擎层** `asyncio.Semaphore` (loop.py:52)，registry 里没有任何 Semaphore。
   中间件只做高危拦截。两者别合并说。
3. "Bash 终极 YOLO" 仅 **CLI 模式**成立；飞书模式 bash 命中 8 条高危正则仍会挂起审批。
4. 飞书放行是**回复文本** `approve <task_id>`，**没有做交互卡片**（不是"点击"）。
5. PLAN/TODO 外部化记忆是 **System Prompt 的 plan-mode 条款强制**（composer.py:27-48），
   `memory/` 包只有 1 行空 docstring，不是代码实现的记忆模块。

### 图漏掉的三个代码亮点（讲架构要主动补）

Recovery 错误码自愈 / SkillTool 按需加载技能 / spawn_subagent 只读子智能体。
内置工具实际 **6 个**（read_file, write_file, edit_file, bash, load_skill, spawn_subagent），
课程图只画了 4 个。

### 模型兼容层措辞定稿（RESUME.md §9 + §5 bullet）

用户原话「对消息和工具调用进行封装，支持双协议兼容」，三处改定：
- **"封装"→"双向翻译 / 归一化"**：封装听着像 CRUD 包装，谁都能写；翻译才是抽象层的实质动作。
- **"支持兼容"→"上层零改动切换"**：兼容是被动适配，零改动才是抽象层的交付物，也是唯一可验证的判据。

## 追加：工具注册与分发亮点总结 + 再修一处虚标

### 工具层五个亮点（已核实，勿依赖记忆）

1. **幻觉容错**（`registry.py:81-84`）：工具名不存在 → 返回 `is_error=True` 消息，不抛异常。
   核心论点：agent 里 404 是**反馈**不是错误，模型下一轮会自己纠正。
2. **失败下沉到输出层**（`registry.py:112`）：`output.startswith("[ERR:")` 自动判 is_error。
   不用异常表达业务失败；同一前缀被 RecoveryManager 解析成错误码，一条链路打通。
3. **拦截伪装成工具失败**（`registry.py:95-99`）：中间件拒绝也返回 is_error=True，
   "被人类拒绝"与"工具报错"对 LLM 是同一种信号。
4. **并发结果按索引回填**（`loop.py:124-144`）：`results[idx] = ...` 而非 append。
   gather 完成顺序不确定 → 用 append 会导致上下文顺序抖动、任务不可复现；
   Anthropic 侧多结果要合并进一条 user 消息，顺序错则语义错。**这是最值得讲的"看不见的坑"**。
5. **调度策略不在 Registry**（`loop.py:52`）：Semaphore(5) 在引擎层，关注点分离。
   加分项：重名注册记 warning（`registry.py:58-59`）；中间件运行时动态挂载（`main.py:178`）。

## 追加：read_file 三层防御改造（修 bug + 输出卸载 + 局部读取）

用户贴课程讲义讲「8000 字符硬截断的局限 + Tool Call Offloading + 全局 Compaction」。
经 AskUserQuestion 确认范围后实施：修 bug + Offloading + offset/limit（不含阈值改 token 级）。

### 🔴 修掉一个只在中文下发作的静默 bug（实跑验证）

旧 `read_file.py:75-79`：**判断用字节 `len(content.encode("utf-8"))`，切分用字符 `content[:MAX_BYTES]`**。
UTF-8 汉字 3 字节 → 中文文件实际返回 8000 字符 = **24034 字节**（阈值 3 倍），
且提示语宣称"截断至前 8000 字节"与事实不符。英文文件完全正常（8034 字节），
所以只在中文内容下发作——本项目注释全中文，一直在吃 3 倍预算。
同类措辞问题：`compactor.py:57` 与 `:64` 把"字符"写成"字节"，一并修。

### 实现的三层防御（`tools/builtin/read_file.py`，255 行）

1. **局部读取** `offset`/`limit`（行号，从 1 开始，输出带行号前缀）
2. **输出卸载** 超阈值 → 完整内容落盘 `work_dir/.claw/offload/<name>__<md5前8位>.txt`，
   回传「行数 + 头尾预览 + 卸载路径 + offset/limit 用法」。同一源文件稳定映射同一卸载文件。
3. **硬截断** 兜底

额外处理：行数 ≤ 60（单行超长 JSON/日志）时行号分段失效 → 退化为**字符头尾预览**并提示用 bash 切片。

### ⚠️ 关键洞察（最有面试价值）

**卸载必须和 offset/limit 配套做**。讲义只说"卸载后倒逼模型按需局部读取"，
但原 `read_file` 没有 offset/limit，模型无法局部读取 →
读全文 → 卸载 → 再读全文 → 死循环；且**现有防线抓不住**：
Reminder 的 MD5 指纹只统计 `is_error` 的失败，卸载 `is_error=False`。
只做一半会制造新 bug。

原 `*.claw/traces` / `*.claw/sandbox` —— gitignore 的单个 `*` **不跨路径分隔符**，
匹配不到 `workspace/.claw/traces`（运行时 work_dir=workspace）。
已验证：旧规则下 `git check-ignore workspace/.claw/offload/` 无匹配。

## 17:55 bash 工具后台任务现状评估 + Go TaskManager 改进方案

### 现状缺陷（tools/builtin/bash.py:62-77，共 6 条）
1. background 分支创建 PIPE 但从不读取 → 64KB 管道写满后子进程阻塞假死。
2. 从不 `proc.wait()` → 僵尸进程 + 退出码丢失。
3. 前台 `asyncio.wait_for(...,30)` 超时只取消 await，未 kill → 进程仍在跑且管道无人 drain（双重泄漏）。
   注意：对外表述"30s 被强制 Kill"与代码不符，代码里没真 kill。
4. 无 Setpgid/setsid → `kill <pid>` 杀不掉 npm 拉起的孙进程；主进程退出后子进程成孤儿占端口。
5. 只返回裸 PID，无 task_id / 无日志回读通道 → 模型只能 `sleep 5` 赌端口。
6. MAX_OUTPUT 8000 硬截断且不落盘 → 超出部分永久丢失。

### 改进方案（Go / internal/tools/task.go）
- TaskManager 单例（sync.Map[taskID]*Task）；Task 持有 Cmd/Cancel/Buffer/Status/ExitCode/PGID。
- Setpgid=true（nohup 等价）→ `syscall.Kill(-pgid, SIGKILL)` 整树回收。
- `Start()` 而非 `Run()`；`Wait()` 放 goroutine 回收僵尸并写回退出码 → 主循环 0 阻塞。
- goroutine + bufio.Scanner 逐行 drain 进 RingBuffer（RWMutex，留最近 2000 行）并落盘 `.claw/tasks/<id>.log`。
- 工具三件套：bash(run_in_background)→task_id / task_output(tail+短阻塞等日志) / task_stop(kill -pgid)。
- 进阶 task_wait_for(pattern,timeout)：等 "ready in 500ms" 再放行，替代 sleep 赌端口。
- 接线：Registry 注册三工具；进程退出 hook 调 Manager.Shutdown() 清场；后台命令也要过 Middleware。

### 状态
仅评估 + 方案，未落地代码。待用户选择：Python 版先修 3 个泄漏 / Go 版完整 task.go / 两者都做。

## 19:25 工具并发调用现状评估（engine/loop.py:128-181）

### 现有机制
- `AgentEngine.__init__` 建 `asyncio.Semaphore(max_parallel_tools=5)`（main.py 未传，走默认 5）。
- `_execute_one` 内 `async with semaphore` 包住 reporter + registry.execute（含 Middleware 链），`asyncio.gather` 并发。
- 结果按 `results[idx]` 回填 → 写入顺序与 response.tool_calls 一致（协议要求，正确）。
- Session 有 `asyncio.Lock`（append / get_working_memory / mark_error_turn / record_usage 全部加锁），无竞态。
- 子智能体 run_sub 独立 `Semaphore(3)` + 最多 10 轮；SubagentTool 作为普通工具在主信号量内 → 最多 5 个子智能体并行。
- 飞书 bot 每条消息 `asyncio.create_task` → 多 session 并发，各自独立 engine/semaphore，无全局预算。

### 已识别问题（未改）
1. **gather 无 return_exceptions**：reporter/Middleware 抛异常 → 整轮崩溃；未回填的 `results[idx]=None` 被 `continue` 跳过 → 孤儿 tool_call → 下一轮请求 DeepSeek 报 400（真 bug，优先级最高）。
2. **无读写分类**：write/edit 并发同文件是 read-modify-write 竞态；只读工具本可更高并发。
3. **信号量范围过大**：飞书审批中间件等待人工确认（≤300s）占着并发位 → 5 个位占满即整轮阻塞（准死锁）。
4. **无全局并发预算**：嵌套子智能体最坏 5×3 并发 LLM 调用；飞书多会话各自限流。
5. ReminderInjector 在批内任一成功即 clear 全表，且一轮可能注入多条重复 nudge。
6. gather 无整体超时；单 bash 30s，超 5 个调用时排队 → 整轮可达 60s+。

### 改法要点（待确认）
只读/写分类（BaseTool.is_read_only 或按文件路径细粒度 asyncio.Lock）→ gather 加 return_exceptions 并补 error 占位 ToolResult → 信号量只包 registry.execute、reporter 移出 → 子智能体并发上限 2 且禁嵌套 → nudge 每轮去重 1 条。
