## 自我盘点：官方 ClientSessionGroup 已覆盖我的 MCPManager（17:45）

**用户质问「有现成包为什么自己实现」** → 核对后发现我确实有重复劳动：
- **协议**用的是官方 `mcp` SDK（2.2.0）✓ 没重复（JSON-RPC/stdio/握手/发现/list/call 全是 SDK 的）
- **但连接管理层重复了**：官方 `mcp.client.session_group.ClientSessionGroup` 实测已提供
  ①多 server 生命周期（async CM）②工具聚合（`group.tools` → `dict[命名空间名, Tool]`，14 项）
  ③**命名空间**（`component_name_hook=fn(name, server_info)`）
  ④**按命名空间路由的调用**（`group.call_tool(全名, args)`——真机调通，返回 server 的 `EISDIR` 报错）
  ⑤read_timeout / progress / **MRTR**（`input_responses`）⑥旧 server 容错（prompts/resources 缺失只 warning）

**结论**：Phase 1 的 `client.py`（连接管理+聚合+命名空间）应改用 `ClientSessionGroup`，预估 210 行 → 80 行。
**必须自己写的**：loader（配置来源与降级）、adapter（Tool→BaseTool）、错误映射（→`[ERR:MCP_*]`）、
审批策略（`mcp__` 前缀）、以及单例/同步 `register_into()` 接缝（因 build_engine 同步 + 飞书每消息重建引擎）。
**甄别标准**：替换后是否丢失本项目既有契约（错误码/审批/BaseTool/同步接缝）——丢契约不能外包，纯复刻 SDK 机制的应删。

⚠️ 教训（已写入 plan §12.9）：原 plan 的模块划分是在**没盘点 SDK 能力**时定的，默认「连接管理自己写」。
正确顺序：**先列 SDK 提供了什么 → 再划自己该写的边界**。
细节：官方 hook 传的是 server 自报名（`secure-filesystem-server`），我用的是配置 key（`filesystem`），
